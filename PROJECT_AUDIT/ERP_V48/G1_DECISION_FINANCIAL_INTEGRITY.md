# G1 — قرار معماري: فرض السلامة المالية على الخادم (BUG-00-03 / BUG-00-04 / BUG-00-05)

## المشكلة بدقة
البيانات التشغيلية تُحفظ نصًا (`value`) داخل مستندات Firestore. القواعد تتحقق أن الكاتب عضو مصرّح له بالمستند، لكنها **لا تستطيع قراءة ما بداخل النص**. لذا الضوابط التالية مفروضة في المتصفح فقط:
| الضابط | أين يُفرض الآن |
|---|---|
| منع تعديل فترة مقفلة | `lockedLedgerChanged` في الواجهة |
| ثبات القيد اليدوي المرحّل/المعتمد | الواجهة (لا زر حذف/تعديل) |
| ثبات الفاتورة/السند بعد الإصدار | الواجهة + بصمات (كشف لا منع) |
| منع الرصيد السالب | تحذير |
| حدود الكوبونات | كتابة ذرّية في مستند مشترك قابل للكتابة لكل عضو |

**ما هو محمي فعلًا على الخادم اليوم:** الإغلاقات المعتمدة (مجموعة `closings` مستقلة بقواعد)، سجل التدقيق (لا تعديل/حذف)، عزل الفروع، الأدوار.

## البدائل
### (أ) خدمة تحقق مالية على الخادم (Render) بحساب خدمة Firebase
العمليات المالية تُرسل إلى `/api/fin/*`؛ الخادم يتحقق (الإقفال، الأرصدة، الحدود) ثم يكتب بصلاحية إدارية؛ وتُمنع كتابة العميل المباشرة للمستندات المالية.
- **يحقق:** كل الضوابط أعلاه، بما فيها منع السالب والكوبونات.
- **التكلفة:** كبيرة — إعادة توجيه مسارات الكتابة المالية كلها، حساب خدمة (سر جديد على الخادم)، الخادم الحالي «مجاني ينام بعد 15 دقيقة» ⇒ **يلزم خطة مدفوعة** وإلا تتعطل العمليات أول دقيقة.
- **المخاطر:** نقطة فشل واحدة (توقف الخادم = توقف القيود)؛ نقطة البيع دون اتصال تتعارض مع التحقق الخادمي الفوري (تبقى البيوع في الطابور حتى الاتصال).
- **المدة التقديرية:** الأطول.

### (ب) نقل السجلات المالية الحساسة إلى مجموعات Firestore مستقلة بقواعد تفحص المحتوى (نفس نهج «السجلات المستقلة للإغلاقات» المعتمد عندك منذ v41.9)
مستند لكل سجل: `fin_journal/{id}`، `fin_invoices/{id}`، `fin_vouchers/{id}`، ومستند `fin_periods/locks` (تاريخ الإقفال). قواعد مثل:
- `create` مسموح فقط إذا `date > get(fin_periods/locks).lockedTo` والمستخدم له الدور.
- `update/delete` للقيد المعتمد **ممنوع** (التصحيح بقيد عكسي كما هو الآن).
- الانتقالات (مسودة ← اعتماد) محصورة بالأدوار المعتمِدة، ولا يعتمد المنشئ قيده.
- **يحقق:** الإقفال، ثبات المرحّل، الاعتماد — **على الخادم فعلًا**. لا يحقق منع السالب ولا حدود الكوبونات (تحتاج تجميعًا لا تستطيعه القواعد).
- **التكلفة:** متوسطة؛ ترحيل **إضافي غير مدمّر** بالنسخ المزدوج (النص القديم يبقى، والسجلات المستقلة تُكتب معه، ثم مطابقة، ثم القراءة منها) — نفس الخطوات التي نُفذت للإغلاقات بنجاح.
- **المخاطر:** منخفضة-متوسطة؛ مجرّب في النظام نفسه؛ يعمل بلا خادم إضافي؛ متوافق مع العمل دون اتصال (Firestore يرسل عند عودة الاتصال وتُطبق القواعد حينها).

### (ج) الإبقاء على البنية مع تقوية الكشف
بصمة متسلسلة لكل سجل مالي، تجميد شهري إلزامي، تنبيه فوري عند أي اختلاف، تقرير «تغيّرات خارج الواجهة».
- **يحقق:** الكشف لا المنع.
- **التكلفة:** صغيرة. **المخاطر:** التلاعب ممكن ويُكتشف لاحقًا فقط.

## المقارنة
| المعيار | (أ) خادم | (ب) مجموعات مستقلة | (ج) كشف |
|---|---|---|---|
| منع تعديل الفترة المقفلة | ✓ | ✓ | ✗ (كشف) |
| ثبات المرحّل والمعتمد | ✓ | ✓ | ✗ (كشف) |
| منع الرصيد السالب | ✓ | ✗ | ✗ |
| حدود الكوبونات | ✓ | جزئي (عدّاد ذرّي بقاعدة) | ✗ |
| يعمل دون اتصال | جزئي | ✓ | ✓ |
| تكلفة تشغيل إضافية | خطة خادم مدفوعة | لا | لا |
| حجم التغيير | كبير | متوسط | صغير |
| خبرة سابقة في مثقال | لا | **نعم (الإغلاقات)** | جزئي |

## التوصية
**(ب) الآن + (ج) تكميلي، و(أ) لاحقًا ضمن جاهزية SaaS (المرحلة 07).**
السبب: يحقق المنع الفعلي لأهم ثلاثة ضوابط (الإقفال، ثبات المرحّل، الاعتماد) بلا تكلفة تشغيل وبلا كسر للعمل دون اتصال، وبمسار ترحيل جرّبناه. منع السالب وحدود الكوبون يبقيان بالكشف حتى (أ).

## خطة التنفيذ إن اعتُمد (ب)
1. قواعد `fin_periods` و`fin_journal` + اختبارات قواعد (لا تمس الإنتاج حتى الدمج).
2. نسخ مزدوج للقيود اليدوية فقط أولًا (الأصغر حجمًا)، ثم الفواتير والسندات.
3. شاشة مطابقة (كما في الإغلاقات) — الناقص/المختلف/الزائد.
4. التحويل للقراءة من المجموعات بعد مطابقة نظيفة — **بموافقتك (G4)**.
5. لا حذف لأي بيانات قديمة في أي خطوة.

**المطلوب منك:** اختيار البديل (أ) أو (ب) أو (ج) أو المزيج الموصى به.
