# G4 — ترحيل القيود اليدوية القديمة إلى السجلات المحمية (الخطوة 4 من المرحلة 01)

**الحالة:** بانتظار قرار المالك. لا شيء يُنفَّذ على الإنتاج قبل الموافقة.

## لماذا لا يكفي زر «ترحيل» عادي
القواعد التي اعتُمدت في G1 صارمة عمدًا، ولذلك ترفض نسخ القيود القديمة كما هي:
1. **القيود في الفترات المقفلة** — الخادم يمنع أي قيد بتاريخ مقفل، وأغلب القيود القديمة كذلك.
2. **القيود المرفوضة** — الإنشاء يقبل «بانتظار الاعتماد» أو «مرحّل» فقط.
3. **المنشئ** — السجل يحمل بريد من ينسخه (المالك)، فيصير القيد المعلّق «قيد المالك» ولا يستطيع المالك اعتماده.

## الخياران
| | (أ) نافذة ترحيل مؤقتة داخل التطبيق — **موصى** | (ب) سكربت على الخادم مرة واحدة |
|---|---|---|
| الطريقة | قاعدة إضافية تسمح للمدير (مع التحقق الثنائي) بنسخ القيود القديمة بعلامة `legacy` وبحالتها الأصلية ومنشئها الأصلي، **فقط** والمستند `fin_periods/migration` مفتوح. يفتحه المالك، يضغط «ترحيل»، ثم يغلقه | سكربت بصلاحيات الخادم يُشغَّل من GitHub Actions مرة واحدة |
| ما تحتاجه منك | ضغطتان: فتح النافذة ثم إغلاقها | إضافة مفتاح حساب خدمة Firebase سرًّا في GitHub |
| المخاطرة | مسار استثنائي موجود في القواعد مدة الترحيل فقط، ومقيّد بالمدير + التحقق الثنائي + سجل تدقيق | مفتاح بصلاحيات كاملة يجب حفظه ثم إلغاؤه |
| التراجع | حذف السجلات `legacy` بسكربت أو بقاعدة مؤقتة؛ الوثيقة الأصلية لا تُمس | مثله |

في الحالتين: **لا يُحذف ولا يتغير أي قيد في الوثيقة الحالية**، والمطابقة تُشغَّل بعدها، والقراءة لا تتحول إلى السجلات إلا بعد مطابقة نظيفة وموافقة ثانية.

## ما سيُنفَّذ بعد الموافقة
1. القاعدة (أو السكربت) + اختبارات المحاكي.
2. زر «ترحيل القيود الحالية» يظهر فقط والنافذة مفتوحة، بعدّاد تقدم وسجل تدقيق.
3. المطابقة: ناقص 0 · مختلف 0 · زائد 0.
4. بعدها خطوة منفصلة: تحويل القراءة إلى السجلات (كما في الإغلاقات v42.2).
