# rbac-permissions

الأدوار والصلاحيات في مثقال (ROLES، scope، tabs، canEditRec، الاعتمادات، MFA) ومطابقتها مع قواعد Firestore. استخدمها لأي تغيير أو مراجعة لمن يرى أو يعدّل أو يعتمد ماذا.

## متى تُفعَّل المهارة
- إضافة دور أو تبويب أو صلاحية.
- مراجعة فصل المهام أو ثغرة وصول.

## متطلبات التنفيذ
- `ROLES` (App.jsx)، `canEditRec`، `editPermOf`، `canApproveJe`، `wfCanAct`، `firestore.rules`، `tests/security/CONSTITUTION.md`.

## خطوات العمل
1. ابنِ مصفوفة: الدور × الإجراء (عرض/إنشاء/تعديل/اعتماد/حذف) × النطاق (فرعه/المسند/الكل).
2. تحقق أن كل صلاحية حساسة مفروضة في القواعد أو الخادم، لا الواجهة فقط.
3. فصل المهام: المنشئ لا يعتمد؛ من يسجل الدفعة لا يعتمد تغيير الآيبان.
4. الأدوار الحساسة (المالية، مسؤول النظام) تتطلب MFA.
5. أي تغيير في `ROLES` ⇐ اختبار قواعد + موافقة المالك.

## المعايير المحاسبية أو الهندسية ذات الصلة
مبدأ أقل صلاحية، فصل المهام (COSO)، OWASP Broken Access Control.

## أمثلة عملية
`accountant_view` يقرأ الدفاتر ولا ينشئ قيدًا؛ اختبار: محاولة إنشاء قيد ⇐ رفض.

> كل الأرقام في الأمثلة وهمية. المستودع عام: لا تكتب بيانات المنشأة الحقيقية.

## حالات الخطأ
- زر مخفي في الواجهة مع قاعدة تسمح ← ثغرة.
- دور جديد بلا اختبار قواعد ← لا يُعتمد.

## اختبارات التحقق
- `npm run test:rules`.
- `node --test tests/editperm.test.mjs tests/useradmin.test.mjs`.

## المخرجات المطلوبة
- مصفوفة الصلاحيات + قائمة الفروقات بين الواجهة والقواعد.

## قواعد عامة
- لا افتراض لقاعدة عمل غير موثقة؛ ارفعها للمالك.
- لا يعتمد المنفذ عمله بنفسه: المخرج يمر على المدقق المستقل المناسب (`accounting-validation-agent` أو `design-quality-auditor` أو `security-auditor`).
- نجاح البناء أو التوازن وحده ليس دليل صحة.
