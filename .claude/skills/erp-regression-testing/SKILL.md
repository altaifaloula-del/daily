# erp-regression-testing

اختبارات الانحدار والجودة في مثقال: اختيار الاختبارات المتأثرة، تشغيل المحرك والقواعد والواجهة، التحقق المحاسبي المستقل، بوابة الجودة، ومقارنة قبل/بعد. استخدمها قبل اعتماد أي تغيير أو إصدار.

## متى تُفعَّل المهارة
- أي تغيير قبل طلب الدمج.
- قبل أي إصدار.
- بعد إصلاح خطأ (اختبار يمنع عودته).

## متطلبات التنفيذ
- أوامر المشروع: `npm test`، `npm run test:rules` (Java)، `npm run test:ui` (Playwright)، `npm run build`.
- إطار الجودة: `node scripts/quality-gate.mjs`، `node --test tests/validation/*.test.mjs tests/ai-team/*.test.mjs`.

## خطوات العمل
1. حدد المتغير: `git diff --name-only main...HEAD`.
2. اختر الاختبارات من خريطة التأثير في `docs/QUALITY_CONTROL_FRAMEWORK.md`.
3. شغّل خط الأساس على `main` واحفظ النتيجة، ثم على الفرع، وقارن (نجح ثم فشل = انحدار).
4. كل خطأ مُصلَح يأخذ اختبارًا يفشل قبل الإصلاح وينجح بعده.
5. شغّل البوابة؛ الفحص الإلزامي الذي لم يُشغَّل = BLOCKED.
6. لا تحذف ولا تتخطَّ (`skip`) اختبارًا قائمًا لتمرير البوابة.

## المعايير المحاسبية أو الهندسية ذات الصلة
هرم الاختبارات: كثير من اختبارات الوحدة للمحرك، قواعد على المحاكي، قليل من اختبارات الواجهة الشاملة.

## أمثلة عملية
تغيير في `buildAccounting` ⇐ `npm run test:acct` + `tests/validation/` + `tests/functional/cycles.test.mjs` + محوّل المحرك.

> كل الأرقام في الأمثلة وهمية. المستودع عام: لا تكتب بيانات المنشأة الحقيقية.

## حالات الخطأ
- اختبار متقلب (flaky) ⇐ يُعلَّم ويُصلَح، لا يُتجاهل.
- بيئة ناقصة (لا Java/لا شبكة) ⇐ يُذكر «لم يُشغَّل» وليس «نجح».

## اختبارات التحقق
- `node --test tests/ai-team/` (سلامة الإطار نفسه).
- `node scripts/quality-gate.mjs --self-test` (البوابة تكتشف الأخطاء المتعمدة).

## المخرجات المطلوبة
- تقرير الانحدار: قبل، بعد، المتأثر، الحكم.

## قواعد عامة
- لا افتراض لقاعدة عمل غير موثقة؛ ارفعها للمالك.
- لا يعتمد المنفذ عمله بنفسه: المخرج يمر على المدقق المستقل المناسب (`accounting-validation-agent` أو `design-quality-auditor` أو `security-auditor`).
- نجاح البناء أو التوازن وحده ليس دليل صحة.
