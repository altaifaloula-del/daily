# api-integration

تصميم وتنفيذ ومراجعة واجهات الخادم والتكاملات الخارجية في مثقال: Express /api، ZATCA، موصل MCP، الذكاء الاصطناعي، البنوك وتطبيقات التوصيل. استخدمها لأي مسار API أو اتصال خارجي.

## متى تُفعَّل المهارة
- مسار جديد في `server*.js` أو تعديل مسار.
- تكامل خارجي جديد.

## متطلبات التنفيذ
- `server.js`، `server-auth.js`، `server-mcp.js`، `server-refs.js`؛ متغيرات البيئة في `.env.example` (لا تقرأ `.env`).

## خطوات العمل
1. التحقق من الهوية: رمز Firebase ID token في كل مسار محمي (`server-auth.js`).
2. التفويض: الدور والفرع والمستأجر من الرمز لا من جسم الطلب.
3. التحقق من المدخلات: النوع، الطول، الحدود؛ رفض الحقول غير المتوقعة.
4. الأخطاء: رمز HTTP صحيح ورسالة عربية بلا تفاصيل داخلية.
5. الاتصال الخارجي: مهلة، إعادة محاولة بتباعد للأخطاء العابرة فقط، مفتاح عدم تكرار للعمليات المالية.
6. السجل: بلا أسرار ولا بيانات شخصية (`server-ailog.js`).

## المعايير المحاسبية أو الهندسية ذات الصلة
OWASP API Security Top 10 (التفويض على مستوى الكائن، المصادقة، الاستهلاك غير المحدود للموارد).

## أمثلة عملية
`POST /api/x` ⇐ 401 بلا رمز، 403 لدور غير مخول، 400 لمدخل خاطئ، 200 للصحيح — أربعة اختبارات على الأقل.

> كل الأرقام في الأمثلة وهمية. المستودع عام: لا تكتب بيانات المنشأة الحقيقية.

## حالات الخطأ
- ثقة بـ `branchId` من الجسم ← ثغرة تفويض.
- عدم وجود حد للحجم ← استنزاف.
- أسرار في `VITE_` ← تُكشف للمتصفح.

## اختبارات التحقق
- `node --test tests/mcp.test.mjs tests/provider.test.mjs tests/useradmin.test.mjs` وما يناسب المسار.
- حالات 401/403/400/200 لكل مسار جديد.

## المخرجات المطلوبة
- عقد المسار + الاختبارات + ملاحظات الأمان.

## قواعد عامة
- لا افتراض لقاعدة عمل غير موثقة؛ ارفعها للمالك.
- لا يعتمد المنفذ عمله بنفسه: المخرج يمر على المدقق المستقل المناسب (`accounting-validation-agent` أو `design-quality-auditor` أو `security-auditor`).
- نجاح البناء أو التوازن وحده ليس دليل صحة.
