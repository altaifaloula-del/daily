# design-system

نظام تصميم مثقال الموحد: الرموز (ألوان، خطوط، مسافات، زوايا، حركة)، المكونات المشتركة، الحالات، RTL/LTR. استخدمها عند استخدام أو إضافة أو مراجعة أي مكون أو رمز.

## متى تُفعَّل المهارة
- إضافة مكون أو رمز.
- مراجعة اتساق الواجهة.

## متطلبات التنفيذ
- `docs/UI_UX_DESIGN_STANDARDS.md` (المرجع)، `PROJECT_AUDIT/ERP_V48/DESIGN_SYSTEM.md`، `styles.js`.

## خطوات العمل
1. ابحث عن مكون قائم قبل إنشاء جديد (`Modal`، `Field`، `Kpi`، `Num`، `RptTable`، `.btn`، `.inp`، `.card`، `.badge`).
2. الرمز الجديد يُضاف لمكان واحد ويُوثَّق في المعايير.
3. الحالات الموحدة: hover حد ذهبي، focus حلقة ذهبية 2px، disabled شفافية 0.5، error حد وردي ورسالة تحت الحقل.
4. الاتجاه: خصائص منطقية (`margin-inline-start`، `inset-inline-end`)؛ الأسهم والأيقونات الاتجاهية تنعكس.
5. الحارس: `tests/brand.test.mjs`.

## المعايير المحاسبية أو الهندسية ذات الصلة
Design tokens (W3C DTCG كمرجع للمفهوم)، WCAG 2.2 AA.

## أمثلة عملية
زر أساسي: `.btn.pri` — لا `style={{background:"#D9A83E"}}`.

> كل الأرقام في الأمثلة وهمية. المستودع عام: لا تكتب بيانات المنشأة الحقيقية.

## حالات الخطأ
- مكون مكرر بشكل مختلف ← يُدمج.
- رمز يُكتب في أكثر من مكان ← مصدر واحد.

## اختبارات التحقق
- `node tests/ai-team/design-lint.mjs`.
- `node --test tests/brand.test.mjs`.

## المخرجات المطلوبة
- المكون/الرمز موثّق مع أمثلة الاستخدام.

## قواعد عامة
- لا افتراض لقاعدة عمل غير موثقة؛ ارفعها للمالك.
- لا يعتمد المنفذ عمله بنفسه: المخرج يمر على المدقق المستقل المناسب (`accounting-validation-agent` أو `design-quality-auditor` أو `security-auditor`).
- نجاح البناء أو التوازن وحده ليس دليل صحة.
